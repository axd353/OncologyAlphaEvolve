# Tabular Foundation Model Variant-Task Experiments

## Brief

This pipeline evaluates discovered priority functions in a different downstream prediction problem from `ExperimentsWithTabularFoundationModels/`.

For each dataset and each tabular foundation model, it builds a suite of predictive tasks where one task equals one dosage variant plus the ancestry coordinates `PC1` through `PC16`. Each task is scored on the full heldout ancestry slice, and the three borrowing schemes are compared by heldout ROC AUC across all variants.

## Overview

For every configured experiment, the runner:

1. Loads the train, calibration, and heldout pickles.
2. Filters heldout rows to the configured target ancestry group using `output_row_tracking.pkl`.
3. Enumerates every dosage column as one predictive task.
4. Fits the requested off-the-shelf model repeatedly for three schemes:
   - `Priority Function Curated Context`
   - `Mixture Learning`
   - `Independent Learning Scheme`
5. Stores per-subject predicted disease probabilities for every scheme and every variant task.
6. Stores per-variant ROC-AUC triplets for the three schemes.
7. Produces one figure per dataset and model with three side-by-side boxplots, with minimal text: scheme names on the x-axis and ROC AUC on the y-axis.

## Procedure

### Predictive task definition

For one dosage variant `dosage__v` and one heldout subject, the model features are:

- `dosage__v`
- `PC1` through `PC16`
- any configured `additional_feature_columns`

The label is the configured `label_column`, typically `phenotype`.

### Scheme behavior

`Mixture Learning`

- eligible context rows: all training plus calibration rows
- if the pool exceeds the effective cap, the runner takes one reproducible random subset and reuses it for all variant tasks

`Independent Learning Scheme`

- eligible context rows: training plus calibration rows matching the target heldout ancestry group
- if the pool exceeds the effective cap, the runner takes one reproducible random subset and reuses it for all variant tasks

`Priority Function Curated Context`

- for each heldout subject and each variant task, the runner reads that subject-variant radius from the priority radius cache
- eligible context rows are reference rows whose ancestry distance to the target subject is at most that radius
- rows are ordered by increasing ancestry distance, then by stable row index
- if no row falls inside the radius, the runner falls back to the single closest ancestry neighbor
- if the eligible set exceeds the effective cap, it truncates to the nearest rows within the radius

This means the priority scheme is both subject-specific and variant-specific in this second pipeline.

## Output

Each run creates one timestamped directory under `output_root_dir`.

Per experiment, the runner writes:

- `heldout_variant_predictions.pkl`
- `heldout_variant_predictions.csv.gz`
- `variant_scheme_metrics.csv`
- `variant_auc_triplets.csv`
- `variant_context_summary.csv`
- `summary.json`
- `priority_radius_cache/`

At the run root, the runner also writes aggregate versions of the same prediction and metric tables plus `summary.json`, `README_run_notes.md`, and a shared `figures/` directory.

### File meanings

`heldout_variant_predictions.*`

- one row per dataset-model-scheme-variant-heldout-subject combination
- includes the predicted disease probability and the heldout lineage columns already used by the first runner

`variant_scheme_metrics.csv`

- one row per dataset-model-scheme-variant
- stores the heldout ROC AUC used for downstream summaries

`variant_auc_triplets.csv`

- one row per dataset-model-variant
- stores the three ROC-AUC values side by side, one for each scheme

`variant_context_summary.csv`

- shared schemes: one row per variant task with the reused context size
- priority scheme: one row per heldout subject and per variant task with the realized radius, selected context size, and fallback flag

## Cache Reuse

Yes. A `priority_radius_cache` generated by `ExperimentsWithTabularFoundationModels/` is directly reusable here, and that is the intended path when the priority function and datasets are unchanged.

No new heavy CPU priority-function evaluation is needed if all of the following still match:

- the priority-function file content
- `function_name`
- training pickle paths
- calibration pickle paths
- heldout pickle paths
- `output_row_tracking_path`
- `supported_ancestry_groups`
- `heldout_target_ancestry_group`
- ancestry columns
- dosage columns

If `priority_radius_cache_path` points to a prior cache directory or to its `manifest.json`, the runner validates those identities before reuse. When validation passes, it links the existing cache into the new run directory and skips rebuilding the subject-by-variant radius matrix. If validation fails, the run stops with a mismatch error instead of silently reusing the wrong cache.

## How To Run Pipeline

Activate the existing project environment and invoke the new module the same way as the first runner:

```bash
source /nfs/home/adas23/python_environments/OcologyAlphaEvolve/bin/activate

  --config ExperimentsWithTabularFoundationModels2/tabular_foundation_models2.example.json
```

```text
ExperimentsWithTabularFoundationModels/output_results/<run_dir>/<experiment_name>/priority_radius_cache
```

or directly at:

```text
ExperimentsWithTabularFoundationModels/output_results/<run_dir>/<experiment_name>/priority_radius_cache/manifest.json
```
